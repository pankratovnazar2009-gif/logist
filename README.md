# Pozna.logist

Веб-приложение (PWA) для польского рынка TSL. Логист указывает **откуда, куда, когда и какой груз** — приложение сразу
показывает подходящих перевозчиков: зарегистрированных в приложении и найденных в открытых FB-группах. Перевозчик
публикует **поездку** («свободен 10–11 октября, еду из Мазовецкого») — и получает подходящие грузы. О новых совпадениях
приходит SMS **без номера телефона**, только со ссылкой на приложение; контакты открываются после подтверждения.

**Одно приложение = один проект Vercel.** Интерфейс и API — один Next.js в корне репозитория:

```
src/app/             — страницы: login, onboarding, loads, offers, matches/[id]
src/app/api/         — API (route handlers): вход по SMS, грузы, поездки, совпадения, внутренние вызовы n8n
src/lib/             — общие типы и правила подбора (matching-rules.ts + тесты), состояния пары (match-state.ts)
src/lib/server/      — серверная логика: Supabase, SMS, GUS, подбор, скрытие контактов
supabase/migrations/ — схема БД (0001_init, 0002_matching, 0003_profile)
```

## Воронка: от поста в FB до подписки

Бизнес-модель (см. [[project-pozna-logist]] в памяти владельца) — восемь шагов, и вот как каждый реализован:

1. **Парсер FB** (n8n, каждые 15 минут) вытаскивает только **заявки на груз** — откуда, куда, что, когда.
   Посты перевозчиков («wolny pojazd» и т.п.) больше не собираются: перевозчиков берём из приложения.
2. **Подбор** сравнивает новую заявку с маршрутами уже зарегистрированных перевозчиков — см. правила ниже.
3. **SMS совпавшим перевозчикам**: маршрут, дата, груз и кнопка «Beriosz?» в приложении (не буквальный ответ
   SMS-ом словом «BIORĘ» — см. «Чего нет» ниже, почему).
4. **Первый нажавший** получает груз; конкурирующим SMS «этот груз уже взят», им — закрытая пара.
5. **Владельцу — SMS** с контактом победившего перевозчика и ссылкой на исходный FB-пост: дальше он сам пишет
   заказчику в Facebook (см. `OWNER_NOTIFY_PHONE` ниже) — это осознанно ручной шаг, приложение в Facebook не пишет.
6. **Через сутки** — n8n дёргает `/api/internal/collect-outcomes`: перевозчику SMS «состоялась ли перевозка» со
   ссылкой на страницу пары; владельцу — напоминание спросить заказчика вручную.
7. **База проверенных** — это и есть `match_requests.outcome`: кто, куда, каким кузовом реально возит.
8. **Подписка** — когда наберётся история сделок, из README и решений владельца: пока не делаем.

## Как работает подбор

Груз и поездка сравниваются по правилам из [src/lib/matching-rules.ts](src/lib/matching-rules.ts):

- регион загрузки должен совпасть; направление сравнивается, если известно с обеих сторон («куда угодно» подходит всем);
- дата погрузки должна попасть в окно поездки **±1 день** (перевозчик 10–11 → грузы с 9 по 12);
- кузов должен подходить (firanka ≈ plandeka), вес и паллеты не должны превышать вместимость. Бус не получит 22 тонны.
  Неизвестное значение пару не исключает.

Пара проходит состояния `pending → requested → confirmed` (или `declined` / `closed`). Когда обе стороны — в
приложении, путь обычный: `request` → `confirm`. Когда одна сторона — пост из FB (подтверждать там некому), доступно
действие `take` — первый нажавший сразу забирает пару, конкурирующие закрываются тем же запросом. Обе ветки —
одна SQL-функция `match_apply`, транзакция с блокировкой строк: два перевозчика не возьмут один груз, двойной клик
безопасен. Контакт (телефон, имя, ссылка на FB-пост) сервер отдаёт **только после подтверждения** — до этого момента
он не виден никому, иначе теряется смысл «первый нажавший выигрывает».

Через сутки после подтверждения `/api/internal/collect-outcomes` (n8n, раз в час) спрашивает перевозчика SMS-ом
«состоялась ли перевозка» → `match_requests.outcome` (`completed` / `failed`). Это и есть база проверенных
перевозчиков из шага 7 — отдельного отчёта по ней пока нет, копится сырыми данными до первых сделок.

## Настройки, тема и язык

В меню аватара (шапка) — «Профиль», «Настройки» и выход. В настройках у каждого пользователя: **тема** (системная / светлая / тёмная) и **язык интерфейса** (polski, English, русский, українська). Выбор хранится в браузере и применяется сразу; по умолчанию берётся системная тема и язык браузера.

- Тексты — в `src/lib/i18n/messages/` (польский — исходник, остальные типизированы по нему: пропущенный ключ не даст собрать проект).
- Цвета — токены в `src/app/globals.css`; тёмная тема переопределяет те же имена под `:root[data-theme="dark"]`.
- SMS всегда на польском латиницей без диакритики (дешевле и одна часть вместо нескольких).

## Деплой на Vercel

1. Vercel → **Add New… → Project** → выбери репозиторий. Framework определится сам (Next.js), Root Directory пустой.
2. Добавь **Environment Variables** (список — в [.env.example](.env.example)). Обязательные: `SUPABASE_URL`,
   `SUPABASE_SERVICE_ROLE_KEY`, `APP_JWT_SECRET`, `INTERNAL_API_KEY`, `SMSAPI_TOKEN` (или Twilio), `GUS_ENV`.
   Необязательная: `OWNER_NOTIFY_PHONE` — личный номер владельца, на него уходит SMS «для груза из FB нашёлся
   перевозчик» (шаг 5) и напоминание спросить результат (шаг 6). Без неё эти два SMS просто не отправляются,
   остальное приложение работает как обычно. Проще всего задать переменные: **Import .env** → файл `.env.vercel`.
3. Deploy. `APP_BASE_URL` задавать не нужно — ссылки в SMS берутся из домена Vercel.
4. Миграции БД — **по порядку**, в Supabase → SQL Editor: [0001_init.sql](supabase/migrations/0001_init.sql), затем
   [0002_matching.sql](supabase/migrations/0002_matching.sql), [0003_profile.sql](supabase/migrations/0003_profile.sql)
   (профиль и бакет для фото), затем [0004_take_and_outcome.sql](supabase/migrations/0004_take_and_outcome.sql)
   (действие «взять груз из FB» + опрос результата через сутки). Каждую — **до** деплоя кода, который её использует.

## FB-группы через n8n

Два воркфлоу в n8n, а не Python-парсер:

**«Logist App — FB → приложение»** (каждые 15 минут):
1. Apify (`facebook-groups-scraper`) отдаёт свежие посты из групп.
2. Gemini определяет, заявка ли это на груз, и вытаскивает маршрут, даты, вес, кузов, телефон. Посты перевозчиков
   («wolny pojazd» и т.п.) отбрасываются — см. воронку выше, шаг 1.
3. Воркфлоу шлёт заявку в приложение: `POST /api/internal/loads` с заголовком `x-internal-key` (= `INTERNAL_API_KEY`).
   Дубли приложение отсекает само — по хешу текста поста.
4. Приложение сразу ищет зарегистрированных перевозчиков и шлёт им SMS (не больше 10 на одну заявку).

**«Logist App — 24 часа: результат перевозки»** (раз в час): дёргает `POST /api/internal/collect-outcomes` —
приложение само находит подтверждённые ≥24ч назад пары и шлёт SMS-опрос (шаг 6 воронки).

Оба используют один и тот же credential (шаблон `{"headers":{"x-internal-key":"{{api_key}}"}}`, `api_key` =
`INTERNAL_API_KEY` с Vercel) — второй воркфлоу подхватывает его сам, второй раз создавать не нужно. Перед включением
первого — проверь credential Apify в узле сбора постов. Оба выключены до готовности; каждый запуск первого тратит
кредиты Apify и Gemini.

Папка `parser/` (Python + Playwright) — прежний вариант парсера, сейчас не используется.

## Чего нет (и почему)

- **SMS «ответь словом BIORĘ»** — буквального ответа на SMS нет: перевозчик нажимает «Beriosz?» в приложении (ссылка
  приходит в той же SMS). Двусторонний SMS (приём ответов) — отдельная интеграция с провайдером (нужен номер,
  принимающий SMS, и вебхук на входящие); не подключена. Итог для пользователя тот же — «кто первый нажал, тот взял».
- Вход через Google (маршрут `/api/auth/google` есть, кнопки во фронтенде нет).
- Push-уведомления в самом приложении — вместо них SMS.
- Ограничение частоты SMS на одного пользователя (сейчас — не больше 10 SMS на одно новое объявление).
- Статус `expired` в БД не проставляется фоном: истёкшие объявления скрываются при чтении.
- Отчёт/рейтинг по базе проверенных перевозчиков (шаг 7 воронки) — данные (`match_requests.outcome`) уже копятся,
  витрины по ним пока нет: рано, пока не наберётся история сделок.
